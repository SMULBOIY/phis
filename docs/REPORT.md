## Abstract

Phishing remains one of the most effective ways to obtain credentials, because it attacks the user
rather than the machine. This project builds, measures and deploys an intelligent phishing website
detection system that classifies a submitted **URL string** as legitimate or phishing using a
supervised machine-learning model, and then reports the result as one of three states —
LEGITIMATE, PHISHING or SUSPICIOUS — where SUSPICIOUS is an explicit *abstention* rather than a
third prediction.

The system is a Flask application served by Waitress, backed by SQLite, with 22 routes, seven
blueprints, a versioned JSON API and a complete audit trail. Three candidate classifiers
(logistic regression, decision tree, random forest) were trained on 164,744 cleaned URLs from the
PhiUSIIL dataset and compared on a 35,302-row validation split; the model and its two decision
thresholds were selected there, and the 35,302-row test split was read once, afterwards.

Measured on the test split, the deployed model reaches **accuracy 0.9839, precision 0.9933,
recall 0.9678, F1 0.9804 and ROC-AUC 0.9981** at the conventional 0.5 boundary. Under the deployed
three-state policy (T_low = 0.05, T_high = 0.95) it abstains on **20.07 %** of URLs and, on the
remaining decisive 79.93 %, reaches **precision 0.9998, recall 0.9977, F1 0.9988** with 30 false
negatives out of 14,722 phishing URLs.

Those figures describe the PhiUSIIL distribution, and the report is explicit about why they are
optimistic for the live web: **100.00 % of legitimate URLs in the dataset use HTTPS against 56.90 %
of phishing URLs**, and a permutation-importance measurement confirms that `has_https` is the single
largest contributor to the model (+0.5840 mean decrease in ROC-AUC, versus +0.3276 for the next
feature). HTTPS is not a safety signal in the real world. The honest claim of this project is
therefore *"a screening aid that is accurate on this dataset and that reports its own uncertainty"* —
not *"a system that is 98 % accurate on the internet"*.

**Keywords:** phishing detection, machine learning, logistic regression, URL lexical analysis,
abstention, calibration thresholds, Flask, scikit-learn.

# Chapter 1 — Introduction

## 1.1 Background

Phishing is a social-engineering attack in which an attacker impersonates a trusted party to induce a
victim to disclose credentials, card details, one-time codes or to install malware. Its distinguishing
property is that the attack targets the user's decision rather than a software defect: a perfectly
patched browser will happily submit a password to `https://paypa1-secure-login.example` if the user
believes the page is genuine.

Because phishing depends on deception at the point of *arrival*, the URL is the last cheap signal
available before the user commits. Blocklists and browser warnings catch URLs that are already known
and already distributed, which leaves a detection gap during the hours in which a fresh campaign is
most dangerous. This is the gap that machine learning addresses: instead of matching against a list,
a model generalises from lexical and structural properties of the URL string — length, dots, digits,
subdomains, the presence of an IP literal, the use of an `@` in the authority, suspicious tokens,
whether the scheme is HTTPS — to a probability that the URL is phishing.

## 1.2 Problem statement

Students and small organisations need a detector that is (a) accurate enough to be useful, (b)
deployable on a laptop or a single server without external services, and (c) honest about its own
uncertainty. Existing student projects in this space typically report a single accuracy figure at a
0.5 threshold, present it as a general capability, and stop. Two failures follow from that pattern:

1. **A confident wrong answer is worse than "I don't know".** A binary classifier always emits a
   verdict, including for URLs whose score sits near the boundary — exactly the population where
   errors concentrate.
2. **Dataset artefacts are reported as model skill.** If the training data correlates a feature with
   the label in a way that does not hold in the real world, the evaluation measures the artefact.

The problem this project solves is therefore twofold: build a working URL-based detection system, and
build it so that its measured claims survive scrutiny — with an explicit abstention state, thresholds
selected on a validation split, a test split touched exactly once, and a limitations section that
names the shortcut the dataset contains.

## 1.3 Aim and objectives

**Aim.** To design, implement, evaluate and deploy an intelligent phishing website detection system
that classifies URLs using machine-learning techniques and communicates uncertainty honestly.

**Objectives.**

| O8 | Document and deploy the system reproducibly | `docs/DEPLOYMENT.md` |

## 1.4 Scope and delimitations

**In scope.** Static analysis of a single URL string submitted by a user or a script; a web interface
and a JSON API; persistent scan history; a dashboard over that history; authentication with roles; a
documented deployment.

**Explicitly out of scope — and why.**

- **No page fetching.** The backend never resolves, connects to or downloads a submitted URL. This is
  a security decision (it removes the server-side request forgery surface and prevents the server from
  being used as a probe) and a scope decision (no headless browser, no HTML analysis, no screenshotting).
- **No DNS age, TLS certificate inspection, WHOIS, reputation feeds or external APIs.** Each would add
  a network dependency, a rate limit and a privacy question; none is required to demonstrate the method.
- **No claim of live-web accuracy.** See §5.7 and the limitations section.
- **No third predicted class.** SUSPICIOUS is an abstention produced by two thresholds over a binary
  model score, never a class the model was trained to recognise. The interface says so.

## 1.5 Significance

The project contributes a complete, defensible reference implementation: a measured baseline for
URL-only detection on a public dataset, a pattern for presenting abstention without misleading the
user, and a security posture (CSP, CSRF, scrypt hashes, per-route rate limits, no outbound sockets)
that a student project can adopt without inventing it from scratch. The negative results are as
useful as the positive ones: the HTTPS shortcut measurement in §5.5 is a concrete demonstration of why
"98 % accuracy" claims about phishing detectors should be read sceptically.

## 1.6 Report structure

Chapter 2 reviews the detection literature and positions the work. Chapter 3 presents requirements,
architecture and the UML models. Chapter 4 documents implementation — data, features, training,
thresholds, application and deployment. Chapter 5 reports measured results, the test campaign and a
discussion that includes the trade-off the selection criterion made. The final sections state
limitations honestly, conclude, and give reproduction commands.

# Chapter 2 — Literature review

## 2.1 The phishing lifecycle and why detection is hard

A phishing campaign has four stages: target selection, lure construction (a URL and a page), delivery
(email, SMS, social), and credential capture. Detection can intervene at any stage; URL inspection
sits between delivery and capture, which is the last moment at which the user can be warned without
inspecting page content.

Three properties make this hard. **Volatility:** a campaign may exist for hours, and URL strings are
cheap to regenerate. **Imitation:** the attacker's goal is to look ordinary, so obviously suspicious
surface features are a choice the attacker can avoid. **Class imbalance and cost asymmetry:** phishing
is rare relative to benign traffic, and the cost of a false negative (a stolen credential) exceeds the
cost of a false positive (an unnecessary warning) — which is why this project optimises for recall
subject to a false-positive constraint, and why it exposes an abstention state instead of silently
trading one error for the other.

## 2.2 Detection families

| Family | Mechanism | Strength | Weakness |
| --- | --- | --- | --- |
| Blocklist / blacklist | Lookup of known-bad URLs and hosts | Near-zero false positives on known entries | Blind to new URLs; requires a feed and therefore network egress and latency |
| Heuristic rule sets | Hand-written rules over URL syntax (IP literal, `@`, many subdomains, long host) | Interpretable, no training data | Brittle; attackers learn the rules; maintenance burden |
| Lexical machine learning | Supervised classifier over features computed from the URL string | Generalises to unseen URLs; cheap; no network | Learns dataset artefacts; cannot see page content |
| Content-based | HTML, DOM, form actions, brand similarity | Strong signal (brand logos, credential forms) | Requires fetching the page — SSRF risk, latency, and the page may cloak |
| Infrastructure / network | DNS age, ASN, TLS certificate, hosting reputation | Hard for attackers to fake quickly | Requires external data sources; privacy and cost |

This project deliberately occupies the **lexical machine-learning** row. It is the family that can be
implemented end-to-end, measured honestly and deployed offline within a single-project scope, and its
main weakness (artefact learning) is measurable — which is why §5.5 measures it.

## 2.3 URL-only lexical features in the literature

Published lexical detectors converge on a similar feature vocabulary: URL length; host length; counts
of dots, hyphens, digits, slashes and special characters; subdomain count; presence of an IP address
in the authority; presence of an `@`; URL-shortener domains; suspicious tokens (`login`, `verify`,
`secure`, `account`, `update`); and scheme. The 15 features used here (Table 4.3) are a direct
instance of that vocabulary, chosen so that each can be computed with the Python standard library
alone, is explainable to a non-specialist, and is reproducible from the string with no I/O.

The literature is also clear about the conceptual trap: features such as HTTPS presence are proxies
for *era and hosting practice*, not for safety. A detector trained on data where benign sites adopted
TLS years before phishing kits did will learn "HTTPS ⇒ benign" and score highly while being blind to
the modern case of phishing hosted on free TLS. §5.5 measures exactly this effect in this project's
own model.

## 2.4 Datasets

Public phishing URL corpora include PhishTank (community-verified, live), the UCI phishing website
dataset, and PhiUSIIL (Prasad & Chandra, 2023), a large corpus of 235,795 labelled URLs with an
associated peer-reviewed methodology for similarity-based detection. PhiUSIIL was chosen because it is
large, publicly downloadable, licence-clear (CC BY 4.0), and — critically — ships a URL column, so the
features used here can be recomputed from scratch rather than read from the published feature table.
That choice is what allows the leakage audit in §4.2 to be meaningful: the split is by URL string
group, not by pre-computed feature row.

## 2.5 Evaluation: thresholds, abstention and honest reporting

Standard classification metrics (accuracy, precision, recall, F1, ROC-AUC, confusion matrix) describe a
decision rule, not a model. Two consequences shape this project:

1. **Metrics belong to (model, threshold) pairs.** Reporting a single accuracy hides the operating
   point. This report always states the boundary, or the threshold pair, alongside the figure.
2. **Abstention is a legitimate output.** Selective classification — refusing to decide when the score
   is inside an uncertainty band — is well established, and it is preferable to emitting a coin-flip
   verdict on the boundary population provided the abstention rate is reported. The user-visible
   wording in this system is written to prevent the opposite reading: SUSPICIOUS means *unresolved*,
   not *probably safe* and not *50/50*.

Threshold selection is a search problem. Here it is a grid over (T_low, T_high) on the validation
split with explicit feasibility constraints — recall ≥ 0.90 on decisive predictions, abstention ≤
0.25, band gap ≥ 0.10 — and a stated objective (maximise decisive F1, tie-break by fewest false
negatives, then lowest abstention, then threshold values). Stating the criterion before seeing the
test split is what makes the test numbers in §5.3 an evaluation rather than a fit.

## 2.6 Positioning and research gap

The gap this project addresses is not a new algorithm. It is the gap between *reported* performance
and *defensible* performance in student-scale detection systems: leak-free splitting, threshold
selection on validation data, a single read of the test split, explicit abstention, and a measured
account of the dataset's dominant shortcut. The contribution is a worked, reproducible example of
that discipline, with all of its code, data provenance and measurements published in the repository.

## 3.2 Architecture

The system is a layered Flask application behind a WSGI server (Figure 3.1 and Figure 3.5).

```
Browser / API client
        │  HTTP
        ▼
Waitress (WSGI)  ──►  Flask application factory: create_app(config, overrides)
                          │
                          ├── 7 blueprints (22 routes)
                          │     core · auth · scanning · dashboard · history · admin · api
                          ├── services/   validation, detection, decision, explanation,
                          │               stats, report, auth, database, http_security
                          ├── ml/         url_utils, feature_extraction, thresholds
                          ├── models/     SQLAlchemy models + PredictionModel wrapper
                          └── extensions  db · login_manager · csrf · limiter
                          │
                          ├──► SQLite (instance/phishing.db)
                          └──► ml/saved_model/{model_bundle.joblib, metadata.json, metrics.json}
```

**Layer rules that are enforced, not merely intended.** Routes never call scikit-learn: they call
`services.detection_service`, which owns the single inference path. Views never compute a metric: they
read `metrics.json` through `services.model_metadata`. The application never opens a socket: feature
extraction is pure string handling over `ml/url_utils.py`. These rules exist because they are what
make the security and honesty claims testable — a second inference path would be a second thing to
audit.

### 3.3.2 Class diagram — `docs/diagrams/class-diagram.svg`

Two layers. The **persistence layer** holds `User` (scrypt hash, role, `is_active`),

The same pipeline as a flow with decisions: CSRF valid? → validate at the trust boundary → hash-verified

Client → TLS reverse proxy → Waitress on loopback → Flask application → SQLite plus read-only model

## 3.4 Data model

Three tables, defined in `models/database_models.py` (SQLAlchemy 2.0):

| Table | Purpose | Key constraints |
| --- | --- | --- |
| `users` | Accounts | unique `username`, unique `email`, scrypt `password_hash`, `role ∈ {user, admin}`, `is_active` |
| `scan_history` | One row per scan (audit trail) | `user_id` nullable with `ON DELETE SET NULL`, `url` ≤ 2048 chars, `features_json` snapshot of the 15 inputs, `prediction ∈ {LEGITIMATE, SUSPICIOUS, PHISHING}`, `model_score ∈ [0,1]`, `risk_level ∈ {LOW, MEDIUM, HIGH}` |
| `model_information` | Seeded audit row for the deployed model | unique (`model_name`, `model_version`), metric columns copied from `metrics.json`, `dataset_fingerprint` (SHA-256), `feature_count` |

The design point worth stating: the *inputs* are stored alongside the output (`features_json`), so a
verdict can be re-explained later without re-running the model, and a stored row is a faithful record
of what the model actually saw — including when the feature code is later changed.

## 3.5 Security design

| Control | Implementation |
| --- | --- |
| No SSRF by construction | Runtime modules contain no network client; submitted URLs are never fetched, resolved or executed |
| CSRF | Flask-WTF `CSRFProtect` globally; token in forms and in `X-CSRF-Token` for `POST /api/v1/scan` |
| Session hardening | `HttpOnly`, `SameSite=Lax`, `Secure` in production, session fixation defence on login |
| Password storage | scrypt via Werkzeug; no plaintext column exists |
| Authorisation | Role check on `/admin*`; per-user scoping on history, export and API reads (401 anonymous, 403 wrong role) |
| Content-Security-Policy | `default-src 'self'; base-uri 'self'; object-src 'none'; form-action 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'` — byte-for-byte asserted by Gate 12 |
| Frame and MIME hardening | `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, HSTS in production |
| Rate limits | Per-route limits (scan, login, register, API) returning 429 with `Retry-After`; no blanket throttle |
| Output safety | Jinja autoescaping everywhere, CSV formula-injection prefixing on export, generic error pages |
| Secrets | `.env` (mode 600, git-ignored); production refuses to start with a missing or short `SECRET_KEY` |

## 3.6 Key design decisions

The decision log (`docs/DECISIONS.md`, ADR-001…044) records the reasoning; the ones that shape this
report are summarised here.

| Decision | Rationale |
| --- | --- |
| Application factory, never a module-level `app` | Enables isolated test applications and per-config construction; without it the 259-case suite and every stage gate could not exist |
| One inference path through `DetectionRegistry` | A second path would be a second security and correctness surface |
| Three states, two thresholds, measured on validation | Abstention must be visible and its thresholds must not be fitted on test data |
| No page fetching at all | Removes SSRF, prevents the server being used as a probe, and keeps the claim honest: this is lexical analysis |
| Metrics read from `metrics.json` at request time | The dashboard and model card cannot drift from the artefact |
| Waitress rather than a dev server | Pure-Python, no root, works identically on Windows and Linux; gunicorn remains available through the same `wsgi.py` |

## 4.3 Feature extraction

Fifteen features, computed from the normalised URL string with the standard library only, in a fixed
order recorded in `metadata.json`:

| # | Feature | Definition |
| --- | --- | --- |
| 1 | `url_length` | characters in the normalised URL |
| 2 | `domain_length` | characters in the registrable host |
| 3 | `num_dots` | count of `.` |
| 4 | `num_hyphens` | count of `-` |
| 5 | `num_special_chars` | count of non-alphanumeric, non-`.:/-` characters |
| 6 | `num_digits` | count of digits |
| 7 | `has_ip_address` | host is an IPv4/IPv6 literal (0/1) |
| 8 | `has_at_symbol` | `@` present in the authority (0/1) |
| 9 | `has_suspicious_pattern` | known pattern such as `//` inside the path (0/1) |
| 10 | `num_subdomains` | label count above the registrable domain |
| 11 | `has_https` | scheme is `https` (0/1) |
| 12 | `is_shortened` | host belongs to a known shortener list (0/1) |
| 13 | `num_suspicious_words` | tokens such as `login`, `verify`, `secure`, `update`, `account` |
| 14 | `has_unusual_port` | explicit non-standard port (0/1) |
| 15 | `has_encoded_chars` | percent-encoded characters present (0/1) |

Normalisation is deliberately minimal and documented: the URL is lower-cased, the scheme defaulted to
`http` when absent, and the host extracted; `mailto:` and similar pseudo-schemes normalise to
`http://mailto:…` — a documented boundary of the validator, not a silent bug. Length is capped at 2048
characters. **No feature requires I/O**, which is what makes the no-egress claim enforceable.

## 4.4 Training

Three candidate pipelines were trained with fixed hyperparameters (`random_state=42`,
`class_weight=None`) and a scaler where the model needs one:

| Candidate | Pipeline | Hyperparameters |
| --- | --- | --- |
| `logistic_regression` | `StandardScaler` → `LogisticRegression` | `solver=lbfgs`, `max_iter=1000` |
| `decision_tree` | `DecisionTreeClassifier` | `max_depth=12`, `min_samples_leaf=10` |
| `random_forest` | `RandomForestClassifier` | `n_estimators=100`, `max_depth=12`, `min_samples_leaf=10`, `n_jobs=1` |

Scaling matters for the linear model because count features (`url_length` spans 0–6000) would
otherwise dominate 0/1 flags under L2 regularisation. `class_weight='balanced'` was rejected on
purpose: the brief prioritises recall over a calibrated prior, and reweighting would change the score
semantics that the abstention band depends on. Fixed hyperparameters rather than a cross-validated
search is a documented limitation (§ limitations, item 8) — the project's claim is methodological
discipline in splitting, thresholds and reporting, not hyperparameter optimality.

## 4.5 Model and threshold selection

Selection happens entirely on the **validation** split; the test split is not read until selection is
frozen (`metrics.json → honesty.test_split_read_before_selection = false`).

Threshold search: all 81 (T_low, T_high) pairs on a 0.05 grid with 0.05 ≤ T_low < T_high ≤ 0.95,
subject to

- recall ≥ 0.90 on decisive predictions,
- abstention rate ≤ 0.25,
- band gap (T_high − T_low) ≥ 0.10,

optimising decisive F1, tie-broken by fewest false negatives, then lowest abstention, then threshold
values. All 81 pairs were feasible for all three candidates, so the criterion discriminated on
objective rather than on constraint. Model selection then uses the same objective across candidates,
tie-broken by validation ROC-AUC.

The result was `logistic_regression` with **T_low = 0.05, T_high = 0.95** — and, as §5.8 discusses,
the highest abstention rate of the three. That trade-off is stated rather than hidden.

## 5.4 What the abstention band actually does

- Of the **474 false negatives** a 0.5 boundary commits to, **444 fall inside the band** and only 30
  survive as decisive errors; of the **96 false positives**, 94 fall inside the band and 2 survive.
  In other words the band removes 538 of the 570 errors the single boundary made, by refusing to
  answer them.
- It is not free: 20.07 % of users are told "unresolved" — roughly one in five scans.
- The state mix (LEGITIMATE 15,018 / SUSPICIOUS 7,085 / PHISHING 13,199) shows the band is not a
  safety net for one class only: it absorbs **5,562 of the 20,580 legitimate URLs** and **1,523 of the
  14,722 phishing URLs** (the two figures sum to 7,085), so abstention costs both classes.
- The measured validation abstention (19.80 %) landed close to the test figure (20.07 %), which is the
  evidence that the thresholds generalised rather than fitted.

`metrics.json → bias_analysis.https_is_largest_feature = true`, and the interpretation stored with the

## 5.8 Discussion

**The selection criterion chose abstention, and that must be defended, not buried.** Logistic
regression was selected on decisive F1 (0.998337) and fewest false negatives (40), and it reached those
numbers by declining 19.80 % of validation rows — roughly 2.6× the tree's abstention. A reviewer is
entitled to ask whether "fewest errors among the cases I chose to answer" is the right objective. For a
warning system where a missed phishing site is the expensive error, yes: an abstention still shows the
user a warning screen, whereas a confident false negative shows a green tick. But the same reviewer is
entitled to demand the cost: one in five users gets no verdict. Both facts are in §5.2 and §5.3.2, and
the interface states the abstention rate nowhere as "accuracy" — the SUSPICIOUS screen says *unresolved*.

**The dataset is the binding constraint, not the algorithm.** Three different model families land
within 0.006 AUC of each other (0.9976–0.9978). That similarity is the signature of a task whose
signal is concentrated in a couple of features (`has_https`, `url_length`, `domain_length` account for
essentially all permutation importance), not of three equally good generalising models. If the
dominant feature is an artefact, all three models share the artefact. This is why §5.5 matters more than
the leaderboard in §5.2.

**One consequence surfaced after this chapter was written and is recorded in full in
`docs/ACCEPTANCE_REVIEW.md` §4.2.** Because no legitimate URL in the corpus contains a path, the
deployed model reads a path or query string as evidence of phishing: appending `/about` to a URL the
corpus labels legitimate moves it from LEGITIMATE to PHISHING. The measurements in this chapter are
unaffected — they reproduce to within 5 × 10⁻⁷ — but they describe a distribution whose negative class
is almost entirely bare homepages. Until the negative class includes deep links and the pipeline is
retrained, the system is a demonstration of the method, not a deployable filter.

**What would change the numbers, for better or worse.** Removing `has_https` would lower every figure
in Chapter 5 and produce a measurement that transfers better. Adding a genuinely independent signal
(domain age, certificate validity window, page-content brand similarity) would raise them on live
traffic — at the cost of the network-free, SSRF-free design that makes this system deployable and
auditable.

**Engineering claims that were verified rather than asserted.** No outbound sockets; one inference
path; one audit row per scan and no re-inference on reads; production refusal to boot without a secret;
CSP unchanged byte-for-byte from the Stage 9 contract; vendored assets unchanged by hash. These are
gate assertions, re-executed on every regression run — which is the only reason to believe them.

# Limitations and threats to validity

Stated plainly, because the value of Chapter 5 depends on the reader knowing what it does not cover.

1. **Static, URL-only analysis.** No page content, redirects, DNS age, TLS certificate, WHOIS, brand
   similarity or reputation feed is consulted, and the backend never visits the submitted URL. A
   phishing page served from a benign-looking URL cannot be detected by this system, and a legitimate
   site with an ugly URL can be flagged.
2. **The evaluation is dataset-bound.** Results describe a held-out sample of the PhiUSIIL (UCI 967)
   distribution. Newer phishing tactics, non-English lures, IDN homographs and mobile-app deep links
   may be under-represented or absent. These are not live-web accuracy figures and must not be quoted
   as such.
3. **The HTTPS shortcut (the dominant caveat).** 100.00 % of legitimate URLs versus 56.90 % of phishing
   URLs in the corpus use HTTPS, and permutation importance confirms `has_https` is the model's largest
   signal (+0.584041 mean ROC-AUC decrease, versus +0.327594 for the next feature). Reported accuracy
   is therefore **optimistic on any traffic where phishing sites also use TLS**, which is most modern
   traffic. HTTPS does not mean a site is safe. An ablation removing `has_https` is required before any
   claim of real-world capability, and is listed as future work.
4. **The path/length artefact — the model is not a usable real-world screener (found in the final
   acceptance review, `docs/ACCEPTANCE_REVIEW.md` §4.2).** In the training corpus **0.00 % of legitimate
   URLs contain a path** whereas 33.59 % of phishing URLs do, and legit URLs have median length 27
   against 38 for phishing. The model therefore learned *path or query ⇒ phishing*, amplified by the
   large positive `url_length` coefficient. Measured on a URL the corpus itself labels legitimate:
   `https://www.saffronart.com` scores LEGITIMATE, the same string with a trailing slash scores
   SUSPICIOUS, and with `/about` appended it scores PHISHING with near-certainty. On an illustrative
   hand-picked sample of 20 well-known benign URLs, 2 were LEGITIMATE (both of them corpus rows),
   7 SUSPICIOUS and 11 PHISHING. Because these scores sit far outside the abstention band, the band does
   not mitigate them. The measured metrics in Chapter 5 remain correct *for this distribution*, but the
   system must not be presented as deployable protection until the negative class contains deep links
   and the pipeline is retrained and re-measured.
5. **Selection favoured high abstention.** The deployed model abstains on ~20 % of URLs — 19.80 % on
   validation, 20.07 % on test — compared with 7.65 % (tree) and 8.82 % (forest). Its high decisive F1
   is *conditioned on answering*: 0.998789 over 79.93 % of cases, not over all cases. Anyone quoting
   0.9988 as a general accuracy figure is misreading the measurement, and this report deliberately puts
   the abstention rate in the same sentence.
6. **Scores are uncalibrated.** `predict_proba` is treated as an ordinal confidence for banding, not as
   a probability that a website is malicious. No Platt/isotonic calibration was applied; the numbers
   0.05 and 0.95 are decision thresholds, not promises that 95 % of PHISHING verdicts are correct.
7. **SUSPICIOUS is an abstention, not a class.** The model is binary. There is no third ground-truth
   label, and a phishing URL inside the band is *unresolved*, never safe — the UI says exactly that.
8. **Hyperparameters are fixed, not tuned.** No cross-validation search was run; depth-capped trees may
   underfit rare patterns and the linear model is limited to a monotone decision surface.
9. **Lexical evasion is unaddressed.** Shorteners, newly registered lookalike domains and compromised
   legitimate domains all have ordinary lexical shapes and can pass.
10. **No cost model.** False positives and false negatives are treated asymmetrically in the *objective*
   but not assigned monetary or operational costs; the abstention cap of 25 % is a design choice, not a
   derived optimum.
11. **Single-node deployment.** Rate limiting uses in-process memory, which is correct for one Waitress
    process and would need shared storage behind multiple workers. SQLite is adequate for coursework
    volume and is not a concurrency solution at scale.
12. **Educational tool.** The system is a screening aid for teaching and demonstration. It must not
    replace user judgement, browser protections or dedicated security tooling, and it explicitly
    refuses to promise that a site is safe.

# Conclusion and future work

## Conclusion

The project set out to build a phishing URL detector that is accurate on a real dataset and honest
about the limits of that accuracy, and it delivered one. The system is complete: a 15-feature lexical
representation, three compared classifiers, thresholds selected on validation data by a criterion
stated in advance, a single read of the test split, 22 routes across seven blueprints, a JSON API, an
audit trail, and a documented production deployment behind Waitress.

Measured on 35,302 held-out URLs, the classifier reaches 0.9839 accuracy and 0.9981 ROC-AUC at a 0.5
boundary; under the deployed three-state policy it abstains on 20.07 % of URLs and reaches precision
0.9998, recall 0.9977 and F1 0.9988 on the remaining 79.93 %, with 30 false negatives. The
methodological claims are verified by gates rather than asserted: leak-free splitting, no test-set
peeking, one inference path, no outbound sockets, unchanged CSP and hash-pinned assets.

The most valuable result is a negative one. Permutation importance shows the deployed model's largest
signal is `has_https` (+0.5840 mean ROC-AUC decrease, versus +0.3276 for the next feature), which
reflects a measured dataset artefact — 100.00 % of legitimate URLs use HTTPS against 56.90 % of
phishing URLs — and not a real-world safety property. Every performance figure in this report should be
read with that sentence in view. The system is honest about its uncertainty by design; this report is
honest about its measurements by the same discipline.

## Future work

| Priority | Work | Rationale |
| --- | --- | --- |
| 1 | **`has_https` ablation study** | Quantifies how much of the reported performance survives removal of the dataset's dominant artefact; the required first step before any external claim |
| 2 | Score calibration (Platt / isotonic) | Turns the band thresholds into statements about observed error rates rather than ordinal cut-offs |
| 3 | Content and infrastructure features behind a sandboxed fetcher | Brand similarity, form actions, certificate window, domain age — with the SSRF surface made explicit and isolated rather than removed |
| 4 | Time-based split and drift monitoring | Today's random grouped split cannot show performance decay; a chronological split can |
| 5 | Cost-sensitive threshold optimisation | Replace the fixed 25 % abstention cap with an explicit cost ratio between the two error types |
| 6 | Multi-process deployment store | Move rate limits and sessions to a shared store to permit more than one worker |
| 7 | Adversarial evaluation | Test shortener, homograph and compromised-domain cases deliberately, and report the miss rate |
